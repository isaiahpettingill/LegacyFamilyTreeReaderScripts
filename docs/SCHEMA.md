# Descriptive Schema Reference

The canonical import schema maps the Legacy Family Tree 9 Access schema into
stable, descriptive SQLite names. `src/legacy_family_tree_reader/schema.py` is
the executable source of truth: schema version 1 catalogs exactly 38 source
tables and 522 source columns. Run `legacy-family-tree schema` to print every
source-to-descriptive column mapping as JSON.

This document explains how to interpret the resulting database. It does not
claim that every opaque vendor flag has been reverse engineered.

## Dataset Merge Model

The normal `import` and `merge` paths create one row in `datasets` for every
source and add `dataset_id` to every imported application row. The source's
Legacy IDs are preserved, not renumbered. Consequently:

- An entity key is `(dataset_id, entity_id)`, never `entity_id` alone.
- All joins between imported tables must include equal `dataset_id` values.
- Numeric IDs can repeat safely in different datasets.
- `datasets.sha256` detects a byte-for-byte duplicate source before import.
- `datasets.source_path`, `imported_at`, `source_format`, and `legacy_version`
  retain provenance.
- Missing source tables are allowed, but unknown columns in a recognized table
  fail import instead of being silently discarded.

For example:

```sql
SELECT i.dataset_id, i.individual_id, i.given_name, i.surname, l.location
FROM individuals AS i
LEFT JOIN locations AS l
  ON l.dataset_id = i.dataset_id
 AND l.location_id = i.birth_location_id
WHERE i.dataset_id = 1;
```

`mdb2sqlite` is different. It keeps original `tbl*` names and appends rows from
all supplied files without `dataset_id`, dataset provenance, or duplicate
protection. A raw database made from several sources cannot recover their row
boundaries later. Import separate raw dumps as separate inputs when isolation
matters.

Cross-dataset identity is intentionally outside the imported records.
`link-person` creates `identity_groups` and `identity_members` on demand. A
membership points to `(dataset_id, person_id)` and does not rewrite any source
ID, relationship, event, citation, or media row. Suggestions do not create
memberships. Family trees and relationship paths remain within one dataset.

## Infrastructure And Views

These tables are generated by the reader and are not among the 38 Legacy
tables:

| Name | Purpose |
| --- | --- |
| `datasets` | Source name, path, SHA-256, import timestamp, source format, and detected Legacy version. |
| `schema_metadata` | One row per mapped source table with descriptive name, description, Legacy version, and reader schema version. |
| `schema_columns` | Source/descriptive column pairs, ordinal, SQLite storage type, and generated description. |
| `identity_groups` | Explicit cross-dataset identity group, created only when identity commands are used. |
| `identity_members` | Unique `(dataset_id, person_id)` membership in an identity group. |

Convenience views are `people`, `marriage_summary`, `families`,
`event_summary`, `citation_summary`, and `media_summary`. Views simplify common
joins but do not replace the underlying tables and retain `dataset_id`.

catalog before assuming a flag's meaning.

## IDs And Relationships

Common ID mappings include:

| Source name | Descriptive name | Meaning |
| --- | --- | --- |
| `IDIR` | `individual_id` | Source-local person identifier. In `media`, this field is mapped to `owner_record_id`. |
| `IDMR` | `marriage_id` | Source-local marriage/family identifier. |
| `IDCR` | `child_id` | Child-link row identifier. |
| `IDER` | `event_id` | Event identifier. |
| `IDET` | `event_type_id` | Event type lookup identifier. |
| `IDEX` | `event_participant_id` | Event participant row identifier. |
| `IDSR` | `source_id` | Master source identifier. |
| `IDSX` | `citation_id` | Citation identifier. |
| `IDIME` | `cited_record_id` | ID interpreted according to citation `type`. |
| `IDBR` | `media_id` | Media row identifier. |
| `IDLR` | `location_id` | Location identifier. |
| `IDAR` | `address_id` | Address/repository identifier. |
| `ID` | `legacy_id` | Additional Legacy row/RIN value where present; it is not the CLI person ID. |

The CLI's `PERSON_ID` is `individuals.individual_id`. A person's parents are
represented by `children.marriage_id` pointing to a `marriages` row, not by
direct parent columns on the person. The marriage supplies
`husband_individual_id` and `wife_individual_id`; relationship types for those
two parent slots are on the child link. Labels reflect Legacy's source schema
even when the records represent other partnership or parent roles.

Zero is commonly used by Legacy as a missing foreign-key sentinel. It is
preserved rather than globally converted to SQL `NULL`; callers should not
assume every non-NULL numeric ID resolves to a row.

## Polymorphic Code Maps

Several Legacy tables use a numeric code plus an ID instead of a conventional
foreign key. The database preserves both values because a single SQL foreign
key cannot express the relationship.

### Event and media owners

`events` and `media` both call the source field `IDType`, but they use different
code maps and even different person/marriage ID spaces.

For `events.record_type`:

| Code | Owner kind | `owner_record_id` target |
| --- | --- | --- |
| `0` | Individual/person | `individuals.legacy_id`, the visible Legacy RIN |
| `20` | Marriage/family | `marriages.legacy_id`, the visible Legacy MRIN |

The query and export layers translate those visible RIN/MRIN values back to
`individual_id`/`marriage_id`. Event participants provide another route from a
person to a shared event. `event_participants.event_record_type` (`IDERType`) is
a denormalized event-owner classification (`0` person, `20` marriage), while
`event_participants.event_id` always targets `events.event_id`.

For `media.record_type`:

| Code | Subject | `owner_record_id` target |
| --- | --- | --- |
| `0` | General person media | `individuals.individual_id` |
| `1` | Person birth media | `individuals.individual_id` |
| `2` | Person christening media (structurally expected) | `individuals.individual_id` |
| `3` | Person death media | `individuals.individual_id` |
| `4` | Person burial media | `individuals.individual_id` |
| `20` | Marriage/family media | `marriages.marriage_id` |
| `30` | Event media | `events.event_id` |
| `40` | Master-source media | `sources.source_id` |
| `41` | Citation-detail media | `citations.citation_id` |
| `70` | To-do media | `todos.todo_id` |

Media paths are split across `media.picture_media_path_id` and
`media_paths.media_path`; relative `media_name` values are resolved against
that base path by exporters. Import does not copy media files. Absolute paths,
relative paths, and URLs remain references and may not exist on another
machine.

### Citation targets

For `citations`, `type` determines the meaning of `cited_record_id`. The
person-facts resolver currently recognizes these Legacy code groups:

| Citation `type` | Resolved target ID |
| --- | --- |
| `0`, `1`, `2`, `3`, `4`, `5`, `15`, `16`, `26`, `27` | Person-level identity or person subfact; `individuals.individual_id` |
| `10` | `alternate_names.alternate_name_id` |
| `12`, `13` | `todos.todo_id` |
| `17` | `children.child_id` |
| `18`, `20` | `marriages.marriage_id` |
| `28` | `stories.story_id` |
| `30` | `events.event_id` |
| `31` | `event_participants.event_participant_id` |

These groups describe how the current person-facts query gathers attached
citations; they do not collapse distinct Legacy citation subtypes. Other codes
are retained but are not guessed. Always filter by both `dataset_id` and
`type`, then join `cited_record_id` to the correct target ID. A citation's
`source_id` independently joins to `sources.source_id` in the same dataset.

### Other code and lookup fields

Many numeric values are foreign keys to dataset-local lookup tables rather
than global enums: event types and roles, source types, marriage statuses,
child statuses, child relationship types, to-do categories/localities, groups,
temples, locations, addresses, and media paths. Join to the corresponding table
instead of hard-coding labels. Legacy 9 `gender` is `0` male, `1` female, and
`2` unknown/unspecified. Privacy flags, LDS statuses, FamilySearch state, tags,
address `Kind`, and media `PicType` remain vendor codes whose interpretation can
depend on context.

## Events, Citations, And Media

An event usually combines:

- `events.event_type_id` to `event_types.event_type_id` for its label and
  narrative configuration.
- `events.event_location_id` to `locations.location_id` for place data.
- `(record_type, owner_record_id)` for its direct owner.
- `event_participants.event_id` for shared-event participants and role IDs.
- A citation with `type = 30` and matching `cited_record_id` for event evidence.

The `event_summary` view resolves the event type and location, but participant,
citation, source, and media data require additional joins.

A citation combines `source_id` with a polymorphic target. Source master data
belongs in `sources`; page/detail, transcription, surety, notes, and citation
format overrides belong in `citations`. The `citation_summary` view resolves
the master source but cannot resolve every polymorphic target in one column.

A media row similarly combines a polymorphic owner, media type/order,
filename/URL, base-path IDs, caption, date, description, sound reference, and
preference flag. The `media_summary` view resolves the picture base path only.
No binary media is embedded into the descriptive SQLite database by import.

## Dates

Legacy's display date fields commonly end in `D` and are imported as text;
associated sort keys commonly end in `SD` and are imported as integers. These
are different representations and must not be interchanged.

An unqualified packed display date commonly has 18 digits:

```text
QQDDMMYYYYFFFFFFFF
```

- `QQ` is a two-digit qualifier.
- `DDMMYYYY` contains day, month, and year; zero day/month supports partial
  dates.
- `FFFFFFFF` contains flags or reserved data.

The display helper decodes this form only when `QQ` and `FFFFFFFF` are all zero
and the remaining calendar components are valid. It also recognizes positive
eight-digit `YYYYMMDD` values. Empty values and sentinels `0`, `-99999999`, and
`99999999` display as missing. A year-only or year/month value is allowed.

Qualified, ranged, flagged, malformed, or unknown values are returned unchanged
by JSON display queries. GEDCOM export converts only unambiguous values and
writes unsupported raw values as `Legacy date:` notes. Sort keys exist for
ordering and matching; they are not proof of the exact display date or
qualifier. Always preserve and inspect the raw `*_date` value before making a
genealogical conclusion.

## Schema Metadata

`schema_metadata` records source table, descriptive table, description, Legacy
schema version, and reader schema version. `schema_columns` records every
source column, descriptive column, zero-based ordinal, SQLite storage type, and
description. For example:

```sql
SELECT source_table, source_column, table_name, column_name, storage_type
FROM schema_columns
WHERE table_name IN ('events', 'citations', 'media')
ORDER BY source_table, ordinal;
```

Metadata describes the supported Legacy 9 catalog, including mapped columns
that may be absent from a particular source export. It does not assert that all
tables have rows or that every vendor code has a known semantic meaning.
